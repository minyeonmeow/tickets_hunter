# settings.json 詳細設定說明

本文件詳細說明在圖形介面中看到的各項設定欄位。

## 介面操作位置

- 開啟後直接顯示「基本設定」。頂端集中開始、暫停／繼續、斷開瀏覽器、自動重整及執行狀態。
- 自動重整間隔也位於基本設定的搶票控制區，與自動重整開關放在一起。
  預設 1 秒，接受任意大於 0 的小數（如 0.01、0.001），實際速度仍受網站、網路及瀏覽器影響；既有設定不會被強制改寫。
- 「斷開瀏覽器」停止目前設定檔對應的搶票實例並釋放連線，保留 Chrome 和設定頁。
  要再次執行請按開始；暫停／繼續則保留原程序的執行狀態。
- 瀏覽器連線方式與 Port 收在基本設定的「瀏覽器連線設定」。
- 連接既有 Chrome 時，開始搶票以作業系統鎖定檢查避免重複實例，不再先掃描所有程序。
  完整程序掃描保留給「強制停止」；TicketPlus 不載入未使用的 OCR 套件與模型。
  OCR 套件在建立辨識器時才載入，其他平台仍保留原本的辨識功能。
  「繼續搶票」仍會重新連接原分頁，保留登入資料；準備期間顯示連接中，並記錄啟動／繼續耗時。
- 拓元選票保留原本關鍵字分組的優先順序與排除設定，先篩選能滿足張數的票種，再依原順序選取。
  多票種頁面只保留目標票種，清除其他已選列；送出前再次核對全表總張數，只有開啟「允許少於設定張數」時才可少取。
  未送出前自行 F5 會重新核對新文件與張數，不再沿用相同網址的完成旗標。
  已送出但結果不明時則保留防重送鎖，暫停、重新連接、F5 或單純經過時間都不會當作送出失敗。
  明確驗證碼錯誤須確認新碼圖才可再試；看不到明確結果時請先查看網站排隊或訂單狀態，不會盲目重送。
  自動辨識模式在明確錯碼後最多自動要求一次換圖；手動模式保留使用者修改，同一張碼圖不會反覆覆寫答案。
  網站明確回覆售完時，只解除同場次、同分頁的提交鎖，再依原本條件偵測票況；一般錯誤不會當作可重送。
  暫停、結束及手動換頁會中止尚未執行的刷新、填寫與提交；網站已接受的工作不會因此撤銷。
  到 `/ticket/checkout` 後狀態為「等待手動處理」，保留目前 Chrome 並停止此實例的自動操作。
  付款方式、資料、結帳送出及取消訂單均交由使用者處理；進入結帳頁不代表購票或付款已完成。
- TicketPlus 保留座位後，在座位確認頁（`confirmSeat`）只會自動按可用的「下一步」。
  活動頁開啟自動選日期時，預設從 API 讀取場次清單與即時活動／場次狀態，再導向對應購票頁，
  不等待場次列表 DOM 或點擊場次按鈕。日期關鍵字依輸入順序逐組比對，同組才使用原排序模式；
  `1/02`、`01/02`、`2027-01-02` 等日期格式可對照，空白分隔仍代表同組條件都要符合。
  排除關鍵字、日期自動遞補、跳過售完設定保留；隱藏、鎖定、過期及未曝光的場次不會被自動選取。
  尚未開賣但已曝光的場次仍可先進入購票頁準備，後續開賣與送出驗證由原流程及網站處理。
  場次清單只需要 `getS3?path=event/{活動ID}/sessions.json`；即時場次狀態最少只需 `get?sessionId={狀態ID}`。
  程式自動沿用公開前端的 ID 格式轉換，並在同一次狀態查詢附上活動 ID，確認活動也可選。
  兩支皆為公開 GET，不傳登入 Cookie 或 Token；不會因取得場次資料而呼叫排隊或保留 API。
  清單預設快取 60 秒，狀態依基本設定的自動重整間隔檢查；關閉自動重整後只在新活動頁或設定變動時讀取一次。
  可將 `advanced.ticketplus_session_api` 設為 `false` 恢復原場次頁方式；
  `advanced.ticketplus_session_api_cache_seconds` 可調整清單快取秒數。選票、送出與手動接手流程不因本設定改變。
  無票刷票時，票區頁預設改用公開 GET API 更新票況；從目前網址取得活動、場次，
  讀取 `ticketAreas.json` 的票區名稱與 ID 對照，僅查詢目前場次的票區及畫面票種。
  對照資料在同次執行中重用；更新時依 ID 合併資料，維持原本票區順序及區域關鍵字優先順序。
  紀錄中的「TICKETPLUS 票區」會顯示票區名稱、ticketAreaId 與餘額；`999999` 顯示為「熱賣中」。
  API 回應會更新原本網頁的票況資料，仍由既有選票、驗證、按下一步、排隊及保留流程接續處理。
  已有選票、正在排隊、暫停或關閉自動重整時不套用；頁面已切換或資料不完整時也不套用。
  API 失敗保留頁面等待下次更新，不因失敗而送出或整頁重新整理。
  目前支援既有票區元件；非票區頁／無法辨識的元件保留原更新方式。
  可在設定檔將 `advanced.ticketplus_stock_api` 設為 `false` 恢復原更新按鈕方式，
  `advanced.ticketplus_stock_api_timeout` 可設定每次 GET 的逾時秒數（預設 5 秒）。
  基本設定的「TicketPlus 實驗模式」可勾選「直接設定選票並呼叫網站送出函式」（預設關閉）。
  同區另有「自訂 enqueue 排隊重試間隔（實驗）」，預設關閉，間隔預設 1 秒，可設任意大於 0 的秒數，包含 0.01、0.001 等小數。
  啟用後只將本站 enqueue 回覆中 `137/Pending` 的正數 `waitSecond` 改為設定值，
  由網站原本唯一的重試流程排程；不另開計時器、不直接重送 POST，也不改成功、錯誤或 reserve 回覆。
  `localCheck: true` 仍先由網站更新票況及檢查可售數量，完成後才開始計算等待秒數，
  所以兩次請求的實際間隔會包含網路及票況更新時間，並非精準定時發送，也不保證更早放行。
  這個選項可獨立開啟；不支援的頁面或已在排隊的本輪會維持網站原流程。
  變更後請斷開再開始，僅在新送出前安裝；重新接手不會清除原有送出防護。
  暫停、斷開或進入確認頁會移除回覆調整；網站已排定或已送出的工作不會因此取消。
  如程序意外失去連線，回覆調整在心跳中斷約 5 秒後失效；不會建立第二組重試接手。
  HAR 的網路回應仍保留網站原始等待值；實驗只調整頁面收到的物件，可由「TICKETPLUS 重試實驗」紀錄確認是否啟用。
  「直接設定選票並呼叫網站送出函式」啟用後依原本關鍵字分組、排序方式及排除設定選區，在同一次瀏覽器操作中呼叫網站內部加票函式，
  不需展開票區或逐次點畫面的加號；網站自身的張數限制與資料更新仍會執行。
  票區不足指定張數會依原優先順序嘗試下一組；張數無法確認時保留現況，不會送出不足張數的選票。
  資格欄位及條款沿用原流程，確認網站選票資料正確後直接呼叫原本 `beforeNext`，
  網站要求資格序號而欄位仍空白時不呼叫送出，也不建立已送出紀錄；補妥後才可接續。
  未送出會分別提示資格、元件就緒、網站下一步驗證或票數不一致；條款未核對成功不再記成已確認。
  由網站自行執行 enqueue、等待及 reserve，不自行重建請求；未另外啟用重試間隔實驗時不改等待時間。
  座位確認頁仍自動下一步；購票資料確認頁停止操作，資料與付款由使用者手動處理。
  模式切換後請斷開再重新開始；若網站元件無法辨識或送出結果未明，不會改按按鈕重複送出。
  直接送出紀錄會在進入資料確認頁時標記為已交接；回到新的選票元件並重新開始，才可建立下一次送出紀錄。
  舊紀錄或結果未明時會顯示「送出防護」，不會把未重新呼叫的舊紀錄誤報為本次已送出，也不會反覆空等 10 秒。
  如果仍停在原購票頁且沒有可確認的結果，可先斷開、手動重整該頁，再重新開始；請先確認網站是否已保留票券。
  進入購票資料確認頁（`confirm`）後停止自動操作並通知使用者接手；資料、條款與後續送出及付款均由使用者處理。
  通知代表等待手動處理，不代表訂單成立或付款完成；確認頁尚未跳轉時不重複點擊。
  詳細執行紀錄中的「TICKETPLUS 耗時」會列出頁面就緒、票數確認、條款處理、點下一步與手動接手的分段耗時。
  「已點下一步」只代表瀏覽器已執行點擊，實際排隊及保留結果仍以網站回應為準。
  排隊期間預設每 0.05 秒檢查瀏覽器已記錄的頁面網址，提早偵測座位確認頁；
  失敗視窗每 0.5 秒檢查、完整排隊文字每 5～10 秒檢查，紀錄會分別標示。
  這些檢查不會重新整理或額外呼叫售票 API，也不會縮短網站要求的排隊時間。
  網址檢查間隔可在設定檔的 `advanced.ticketplus_queue_url_poll_interval` 調整，單位為秒，範圍 0.02～1。
  詳細執行紀錄的「TICKETPLUS 排隊計時」會分別記錄：點擊送出、enqueue／reserve 請求、
  回應標頭與接收完成、收到瀏覽器跳轉通知、監控偵測、開始處理座位頁、讀取頁面及下一步點擊返回。
  「排隊摘要」集中顯示各段耗時；請求至回應使用瀏覽器計時，其餘使用程式收到事件／執行階段的高精度計時。
  送出至跳轉通知包含網站等待、網路及前端處理，不能只憑 HTTP 200 認定座位已保留。
  事件傳遞順序可能讓監控先於跳轉通知記錄，摘要會保留正負時間差，避免誤算成網站等待。
  偵測到確認頁後直接接續處理，省去返回主迴圈及重複讀取網址；確認頁仍只按可用的座位「下一步」，
  購票資料確認頁保留手動處理。事件監聽不讀取回應本文、Cookie 或憑證，不會重送請求。
  可將 `advanced.ticketplus_queue_timing` 設為 `false` 關閉詳細事件計時；一般分段計時仍保留。
  事件計時涵蓋 `queue.ticketplus.com.tw` 的 enqueue、`api.ticketplus.com.tw` 的 reserve 與
  getUserCurrentReservedOrder；只記錄端點名稱與耗時，不記錄查詢參數或回應本文。
  座位頁自動下一步會等待實際座位元件、票券資料與按鈕就緒，並確認按鈕未被遮罩覆蓋，
  避免網址剛變但元件尚未準備好時誤點。尚未就緒會顯示等待原因，再於後續輪詢檢查。
- 本機 Python 版本的 TicketPlus 預設會在設定頁開啟或切換到該設定檔時，預先載入獨立工作程序。
  列表顯示「程序待命」代表尚未開始搶票，也尚未連接 Chrome；按開始才接手瀏覽器。
  暫停保留當次流程，繼續時重新連接；斷開結束當次任務，程序留待下次開始使用。
  關閉設定頁或結束程式會清理工作程序並保留專用 Chrome；強制停止會終止該實例的程序。
  可在設定檔將 `advanced.warm_ticketplus_worker` 設為 `false`，恢復每次開始才啟動程序的方式。
  目前此方式僅支援 TicketPlus 連接既有 Chrome；其他平台與打包版維持原流程。
- FunOne 已移除活動頁自動按下一步，請先手動進入票區。程式可提前準備張數、條款與已出現的驗證碼。
  「指定開始時間」用於限制購買送出時間，不會在 FunOne 購票頁到點時重整整頁。
  留空則等待網站購買按鈕可用後處理；自動送出仍由驗證碼設定中的「自動送出」控制。
  FunOne 有指定時間時會預先取得網站時間（台灣時間），優先監聽 GetNowTime 回應；
  必要時由目前頁面補查；網站時間僅供參考，指定時間預設依校準後的國家標準時間觸發。
  標準時間到點而購買仍不可用時，若「自動重整」開啟，會嘗試網站的「更新頁面」，
  保留預選、不做整頁 F5，並遵守 Cookie 與約 30 秒冷卻。
  網站時間差包含秒精度與網路誤差；取得網站時間失敗不影響操作，但國家標準時間尚未校準或過期時，指定時間送出會等待校時。
  網站時間參考資訊會顯示在基本設定的執行狀態旁。
- 實例列表的「強制停止」會結束同專案、同實例的搶票程序，保留 Chrome 與設定服務。
  適用於斷開無反應或殘留程序占用連線；完成後可重新按開始。不要用它代替日常暫停。
- 原執行階段改為「實例與排程」，供多開管理及選用的定時暫停設定使用。
- 底部保留儲存設定、重設與「結束程式」；結束程式會停止所有搶票實例與設定服務。
  儲存設定先寫入完整暫存檔再替換原檔，讀取時會短暫重試 Windows 檔案替換衝突，避免讀到空白或半份設定。
  儲存失敗時顯示失敗並保留原檔，不會繼續以「儲存成功」開始新任務。
- 使用須知整頁及社群連結先以 HTML 註解封存，日後需要時可恢復。
- 連線或選分頁失敗會跳出錯誤通知，並在實例列表保留原因；同一則錯誤不會每次輪詢重複跳出。
  暫停代表程序保留待命，停止中則等待斷線完成；離線實例不再顯示為執行中。
- 區域關鍵字以分號分組並依輸入順序優先比對，例如 `A區;B區;C區`。
  FunOne 先篩掉無法購買的票種，再依關鍵字優先順序選擇；同組多個結果才套用區域排序方式。

## 保存登入與連接既有 Chrome

預設使用「連接已開啟的專用 Chrome」，Port 為 **19327**。

1. 雙擊專案根目錄的 `start-browser.cmd`，輸入 Chrome 連接 Port，或按 Enter 使用預設值。
2. 在開啟的 Chrome 登入售票網站，並開好要操作的購票頁面。
3. 執行 `start-settings.cmd`，不會詢問 Port。腳本中的 `TICKETS_CHROME_PORT` 預設為 19327，
   如瀏覽器使用其他 Port，先用記事本修改這個數字，使兩者相同。
   啟動時會寫入 Chrome 連接 Port，介面自動帶入。設定網頁 Port 沿用設定，預設 16888。
4. 購票網址需與已開啟的購票頁面為相同網站。儲存設定後按開始，程式會接手既有分頁，
   不重新導向首頁、不注入設定中的舊登入 Cookie。

「暫停」會停止操作並斷開連接，瀏覽器保持開啟；「繼續」重新連接原分頁。
「結束」會停止搶票程序並斷開，仍保留 Chrome。暫停期間不偵測票況。
「停止自動重整」是獨立功能，仍保持連接與票況偵測。

關閉最後一個設定頁面後，約 5 秒會自動停止搶票程序、結束設定服務並釋放設定網頁 Port。
重新整理頁面或仍有其他設定分頁開啟時，不會結束服務。專用 Chrome 保持開啟。
重新啟動設定服務會先通知殘留的舊搶票程序結束，且不再清除暫停狀態而使舊程序恢復；
需自行按「開始」才會啟動新的搶票程序。命令視窗按 Ctrl+C 也會通知搶票程序結束。

瀏覽器也可保留參數用法，例如 `start-browser.cmd 19328`，明確指定時不再詢問。
設定腳本若需配合，將 `set "TICKETS_CHROME_PORT=19327"` 改為 `set "TICKETS_CHROME_PORT=19328"`。
Chrome 連接 Port 與設定網頁 Port 不可相同。變更後需結束舊搶票程序再開始。
每個 Port 的登入資料分別保存在 `%LOCALAPPDATA%\TicketsHunter\Chrome-<Port>`，
重新開啟相同 Port 就會沿用資料；網站若讓登入過期仍需重新登入。

同一 Port 同時只允許一個搶票實例控制，暫停期間也保留使用權。
多開時使用不同 Port 與不同設定檔。若相同網站有多個分頁，請保留要操作的一個，
或先切到目標購票分頁再開始；繼續時固定接回原分頁。
瀏覽器未開、Port 不符或目標分頁已關閉時，程式會提示並結束，請確認後再按開始。

連接埠只用於本機連接。請勿將瀏覽器資料夾分享給別人，內含登入資料。
進階設定仍可改回「由程式開啟新的 Chrome」，此模式維持原本結束時關閉瀏覽器的行為。
Chrome 啟動參數（例如代理、擴充功能、無頭模式）在連接後不會套用，需於啟動瀏覽器時設定。

程式支援「即時套用」功能：**搶票中修改設定後儲存，程式會在 1 秒內自動套用新設定，不需要重新啟動。**

### 刷新在指定時間（refresh_datetime）
選填 | 型別：字串 | 預設：空白

在指定時間到達前，程式會持續等待並顯示倒數；時間到達後，依自動重整設定重新載入並開始處理。
FunOne 購票頁可提前預選，時間到才允許購買送出，不會整頁重整而清除預選。

**格式**：YYYY/MM/DD HH:MM:SS（24小時制）

**範例值**：2025/12/25 14:00:00

**使用情境**：
- 已知演唱會下午2點開賣
- 提前開啟程式並導航到售票頁面
- 程式會在 2025/12/25 14:00:00 自動重整頁面並開始搶票

**提示**：建議設定比開售時間早 1-2 秒，補償網路與處理延遲。

**停用**：留空即可

### 指定時間使用國家標準時間（UTC+8）

預設啟用，適用於所有平台的指定開始，以及「實例與排程」的定時暫停、繼續。
程式向[官方 NTP 服務](https://www.stdtime.gov.tw/chrono/index_2_2.html)校時，以單調計時器持續推進，
不修改 Windows 系統時鐘，也不會因本機手動調整時間而直接改變倒數。
NTP 連線失敗時，可改用[官方網站時鐘](https://www.stdtime.gov.tw/home/WebClock)的 HTTPS 時間作備援，介面會標示為「估算」。

在基本設定的指定開始時間下方，可查看目前時間、校時狀態與「標準減本機」的差距，或按「立即校時」。
例如 `+200 ms` 代表本機慢約 0.2 秒；`-200 ms` 代表本機快約 0.2 秒。
顯示毫秒不代表毫秒級準確度，仍受網路延遲、路徑不對稱及電腦處理影響。
設定服務與各搶票程序分別校時，因此顯示值可能有小幅差異。

初次校時尚未成功或資料超過有效時間時，指定開始、定時暫停與繼續會等待，**不會自動改用本機時間**。
未設定指定時間的一般操作不必等待校時。若需要使用原本機時間，取消此選項、儲存並重新開始實例。
修改程式後須先重啟 `start-settings.cmd`，再重新開啟設定頁及開始實例。

進階校時設定保留在設定檔的 `advanced`：

| 設定 | 預設值 | 用途 |
|------|--------|------|
| `standard_time_enabled` | `true` | 使用國家標準時間 |
| `standard_time_servers` | `["time.stdtime.gov.tw", "clock.stdtime.gov.tw"]` | NTP 伺服器，最多四個 |
| `standard_time_timeout` | `1` | 每次連線逾時秒數 |
| `standard_time_sync_interval` | `300` | 成功後背景重新校時的間隔秒數，至少 30 秒 |
| `standard_time_max_age` | `900` | 樣本有效秒數；過期會等待校時 |
| `standard_time_retry_interval` | `30` | 失敗後重試秒數，至少 5 秒 |
| `standard_time_https_fallback` | `true` | NTP 失敗時使用官方 HTTPS 備援估算 |

「立即校時」也有至少 5 秒的節流，且同一程序不會重疊發出校時工作；畫面每秒更新不代表每秒向官方查詢。

#### 日期自動遞補 ⭐ 新功能
型別：布林值 | 預設：**關閉**（嚴格模式）

當所有日期關鍵字都比對失敗時的行為控制。

在圖形介面中顯示為：**日期自動遞補** (開關按鈕)

**可選值**：

| 開關狀態 | 中文說明 | 行為描述 |
|---------|---------|---------|
| **關閉** | **嚴格模式**（預設） | 關鍵字全失敗時**停止執行**，等待手動介入 |
| 開啟 | 自動遞補模式 | 關鍵字全失敗時**自動遞補**，使用「日期排序方式」選擇可用日期 |

**功能說明**：
- **嚴格模式（推薦）**：避免誤購不想要的場次
  - 關鍵字設定錯誤時會停止並等待修正
  - 適合對日期有嚴格要求的使用者
- **自動遞補模式**：確保程式持續執行
  - 即使關鍵字設定錯誤也會自動選擇
  - **風險**：可能購買到不想要的場次

**使用建議**：

| 使用情境 | 建議設定 | 原因 |
|---------|---------|------|
| 只想買特定日期（如：11/16） | 關閉 | 避免買到錯誤日期 |
| 任何日期都可以接受 | 開啟 | 確保能搶到票 |
| 混合策略 | 根據重要性決定 | 日期重要用「關閉」，不重要用「開啟」 |

**實戰範例**：
```
情境：只想買 11/16 的票

在圖形介面中設定：
- 日期關鍵字：11/16
- 日期自動遞補：關閉

結果：
✅ 若找到 11/16 → 選擇該日期
❌ 若找不到 11/16 → 停止執行，等待手動介入（不會自動選其他日期）
```

## 驗證碼設定

### 猜測驗證碼（ocr_captcha）

#### OCR 辨識方式（provider，實驗）

在「進階設定」的 OCR 設定可選擇「本機模型（ddddocr）」或「百度雲 OCR」。預設仍為本機模型。
百度模式目前接入拓元與 FunOne，參考 [Interpark 專案的 OCR 選用方式](https://github.com/michelle11032424-jpg/Interpark-/blob/main/interpark-ticket-main/runner.py)，

   - 顯示訊息：`[CITYLINE LOGIN] Email entered: vic***`
   - 提示：`[CITYLINE LOGIN] Please manually enter password and click login button`

2. **手動輸入密碼**
   - 在瀏覽器視窗中輸入您的密碼

3. **到信箱收取驗證碼**
   - Cityline 會傳送驗證碼到您的註冊信箱
   - 開啟信箱，找到驗證碼
   - 在登入頁面輸入驗證碼

4. **完成 Cloudflare Turnstile 驗證**
   - 登入頁面會顯示 Cloudflare Turnstile 驗證（類似 reCAPTCHA）
   - 程式會自動等待驗證完成（登入按鈕從 `opacity: 0.3` 變為 `opacity: 1`）

5. **手動點擊登入按鈕**
   - 所有驗證完成後，**手動點擊「登入」按鈕**
   - 程式會自動偵測登入完成（URL 變化或 DOM 元素出現）
   - 顯示：`[CITYLINE LOGIN] Login completed after Xs`

   - 登入成功後，程式會：
     - 自動重新導向到目標活動頁面（`[CITYLINE LOGIN] Redirecting to target page...`）

**時間限制**：
- ⏱️ 程式會等待最長 **5 分鐘**（300 秒）供您完成手動登入
- 每 10 秒顯示一次等待提示：`[CITYLINE LOGIN] Still waiting... (Xs elapsed)`

**為什麼不能全自動登入？**
- Cityline 使用 **Email 驗證碼**（需要收信）
- Cloudflare Turnstile 驗證需要真實使用者互動
- 使用 **HttpOnly Session Cookie**，無法透過程式碼存取
- 半自動模式在安全性與自動化之間取得平衡

**設定位置**：
- 在圖形介面中找到「進階設定」→「帳號密碼設定」→「cityline」
- 只需填寫**帳號（Email）**，密碼欄位可留空

- 啟用 — 接受不相鄰座位，提高選到票的機率

**支援平台**：iBon、年代（Ticket）、KHAM、Ticketmaster

**使用情境**：多人同行搶票時，若連座數量不夠，啟用此選項可改為接受非連座位置，降低選票失敗率。

### Telegram Bot 通知

> ⭐ v2026.03 新增

#### Telegram Bot Token（telegram_bot_token）
型別：字串 | 預設：空白

Telegram Bot 的 API Token。留空則停用 Telegram 通知。

在圖形介面中顯示為：**Telegram Bot Token**（文字框）

#### Telegram Chat ID（telegram_chat_id）
型別：字串 | 預設：空白

接收通知的 Telegram 聊天室 ID。多個 ID 請用逗號隔開。

在圖形介面中顯示為：**Telegram Chat ID**（文字框 + 測試按鈕）

**功能說明**：
- **訂單成功時**：傳送「[平台名稱] order success! Please checkout and pay ASAP」
- 支援同時傳送到多個聊天室（逗號分隔 ID）
- 通知不會影響搶票流程（使用非同步傳送，3 秒逾時）
- 可與 Discord 通知同時啟用，兩者互不影響

**如何建立 Telegram Bot**：

1. **開啟 BotFather**
   - 在 Telegram 搜尋 `@BotFather` 並開啟對話
   - 或直接點擊：https://t.me/BotFather

2. **建立新 Bot**
   - 傳送 `/newbot`
   - 依照提示輸入 Bot 名稱（顯示名稱）
   - 再輸入 Bot 使用者名稱（必須以 `bot` 結尾，例如 `MyTicketBot`）

3. **取得 Bot Token**
   - BotFather 會回覆一串 Token，格式類似：`123456:ABC-DEF1234ghIkl-zyx57W2v1u123ew11`
   - 複製這串 Token 貼到設定介面的「Telegram Bot Token」欄位

4. **取得 Chat ID**
   - 在 Telegram 搜尋 `@userinfobot` 或 `@RawDataBot` 並開啟對話
   - 傳送任意訊息，Bot 會回覆您的 Chat ID（一串數字）
   - 如果要傳送到群組，先將您的 Bot 加入群組，再用 `@RawDataBot` 在群組中取得群組 Chat ID（通常為負數）

5. **跟 Bot 對話（必要）**
   - 在 Telegram 搜尋您剛建立的 Bot（用 `@您的Bot名稱`）
   - 按下 **Start** 或傳送 `/start`
   - ⚠️ **未執行此步驟，Bot 無法傳送訊息給您**（Telegram API 限制：Bot 只能回覆曾主動對話過的使用者）

6. **貼到設定介面**
   - 在「進階設定」頁籤找到「Telegram Bot Token」和「Telegram Chat ID」
   - 分別貼上 Token 和 Chat ID
   - 點擊「測試」按鈕確認設定正確
   - 儲存設定

**注意事項**：
- Bot Token 是敏感資訊，請勿分享給他人
- 多個 Chat ID 之間用逗號隔開，例如：`123456789, 987654321`
- 留空 Token 或 Chat ID 則停用 Telegram 通知
- 通知失敗不會影響搶票流程
- 如果測試顯示「chat not found」，請確認您已跟 Bot 對話過（步驟 5）

## 多開實例

「多開」= 同時跑多個搶票實例，涵蓋三種情境：不同平台同時搶、同平台不同活動、不同帳號分散風險。

### 用圖形介面管理

1. 上方「實例設定檔」列預設有 `default`（即 `settings.json`）。
2. 點「＋ 新增」選平台 → 自動以目前設定為底建立 `profiles/<name>.json`，並帶入該平台 homepage。
3. 切換 profile 分頁，各自編輯關鍵字、帳號、homepage 並獨立存檔。
4. 在各 profile 分頁按「搶票」，即以該設定檔啟動一個實例。
5. 「執行階段」頁籤的「執行中實例」面板：列出每個實例的存活（心跳）、執行/暫停狀態與執行網址，可逐一暫停／繼續，或「全部暫停」。
6. 對已在執行的 profile 再按「搶票」會跳確認框，確認後以序號（如 `kktix-2`）開第二個實例。

### 注意事項

- **一實例一帳號**：同帳號同活動多開會被平台踢 session。
- **KKTIX**：多開可能打亂自身排隊順序、甚至被匯入假排隊，請斟酌。
- **改帳號需重啟實例**：帳號/Cookie 不在熱載白名單，改完要重開該實例才生效。
- **暫停為 per-instance**：暫停一個實例不影響其他；「系統時間／秒數 - 暫停關鍵字」定時排程也各實例依自己設定生效。
- 開發者參考：機制細節見 `docs/03-mechanisms/17-multi-instance.md`。

## ❓ 常見問題

### Q1: 圖形介面和 settings.json 哪個優先？  
**A:** 圖形介面修改後會自動儲存到 settings.json。
---

### Q2: 修改設定後要重新啟動嗎？
**A:** 大部分設定**不需要重新啟動**！程式支援「即時套用」功能，搶票中修改設定後儲存，程式會自動偵測並套用。

**可以即時套用的設定**（不需重啟）：
- 張數、日期/區域關鍵字、排除關鍵字
- 日期/區域自動遞補、排序方式
- 刷新間隔、刷新在指定時間
- 輸出除錯訊息、音效通知
- OCR 驗證碼設定
- 優惠代碼、使用者自定字典
- Discord Webhook URL
- 聯絡人資訊
- KKTIX、拓元平台專用設定

**需要重新啟動的設定**：
- 售票網站網址
- 瀏覽器
- 無圖形界面模式、視窗大小
- 設定介面 Port、Proxy
- 所有帳號密碼和 Cookie

---

### Q3: 可以同時用多個設定檔（多開）嗎？
**A:** 可以，有兩種方式：

- **圖形介面（推薦）**：上方「實例設定檔」列點「＋ 新增」選平台建立 profile，每個 profile 是獨立設定檔，可各自「搶票」成一個實例。詳見[多開實例](#多開實例)。
- **命令列**：複製 settings.json 並改名，啟動時指定：`nodriver_tixcraft.exe --input settings_A.json`

⚠️ 同一活動、同帳號多開會被平台踢登入（session 互踢）；安全用法是「一個實例一個帳號」。

---

### Q4: 可以備份設定檔嗎？
**A:** 可以！複製 settings.json 並改名即可備份。

---

### Q5: 系統支援哪些語言？

**A:** 系統針對不同功能提供多語言支援：

- 「即將開賣」偵測：支援「即將開賣」、「Coming Soon」
- 「售完」偵測：支援「已售完」、「Sold Out」

- 關鍵字設定「週六 19:30」（繁體中文）

## 全域自動重整開關（2026-10-26）

設定介面 → 執行狀態 → 全域自動重整：

- 按「關閉自動重整」後，可自行按 F5；程式持續偵測目前頁面，依原設定選票。
- 關閉的是程式的整頁重整、相同網址重載、票況／座位更新按鈕及刷新復原流程。
- 正常登入與購票跳頁、驗證碼換圖仍運作；網站自身的更新不受此開關控制。
- 所有平台及所有實例共用，切換不需按儲存，並保留至下次啟動。
- 首次升級須重新啟動設定服務與搶票實例，載入新版後即可在執行中切換。
- 關閉刷新不代表能看到伺服器最新庫存；靜態頁面仍需自行 F5 才能更新票況。
